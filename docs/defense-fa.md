# راهنمای دفاع اعضای گروه

اعضا: پوریا امیرنیا، دانیال آذرنیا، محمدجواد خوشدونی فراهانی، محمدمتین انصاری.

**نکته مهم:** انتساب کار باید براساس مشارکت واقعی و تاریخچه Git هر فرد تکمیل شود؛ تقسیم زیر صرفاً پیشنهاد برای تمرین و اختصاص کار واقعی است، نه ادعای انجام آن توسط افراد.

## نقشه معماری

`configs` -> Build (release/ASan+UBSan) -> Execute both versions -> Detect -> Compare with independent oracle -> Diff correlation -> Delta debugging -> Replays and regression test -> JSON/Markdown -> CI exit.

## پیشنهاد برای مشارکت و دفاع

- پوریا امیرنیا: راهبری CLI، منطق کدهای خروج و CI (`patchguard/cli.py`، `.github/workflows`). سؤال نمونه: چرا `40` نسبت به `20` اولویت دارد؟ چون بدون شواهد کافی نمی‌توان PASS یا دسته‌بندی قطعی داد.
- دانیال آذرنیا: اجرای واقعی و شناسایی خطا (`runner.py` و `detection.py`). سؤال نمونه: تفاوت SIGSEGV با ASan stack-buffer-overflow؟ اولی فقط نشانه توقف است و دومی تشخیص مستند نوع دسترسی حافظه.
- محمدجواد خوشدونی فراهانی: تحلیل Diff و محافظت‌ها (`correlation.py` و `hardening.py`). سؤال: آیا PIE به معنی روشن بودن ASLR است؟ خیر؛ PIE قابلیت جابه‌جایی باینری است، ASLR به سیستم اجرا هم بستگی دارد.
- محمدمتین انصاری: کمینه‌سازی و ورودی‌های بازتولید و آزمون‌های منفی (`minimize.py` و `tests`). سؤال: چرا کمینه‌سازی بر اساس هر exit!=0 اشتباه است؟ چون باید همان نوع خطا و محل مرتبط را حفظ کنیم.

## آزمایش ۳۰ ثانیه‌ای

در محیط Linux/WSL2 با `libjson-c-dev`, `gcc`, `binutils`, `git`:

```bash
python3 -m patchguard --config configs/frame-correct.json --out artifacts/demo --allow-local
python3 -m patchguard --config configs/frame-incomplete.json --out artifacts/demo-incomplete --allow-local
python3 -m patchguard --config configs/frame-regression.json --out artifacts/demo-regression --allow-local
```

کدهای خروج مورد انتظار به‌ترتیب `0`, `10`, `20` است. برای نگه‌داشتن اجرای shell پس از کد ۱۰ یا ۲۰، `echo $?` را جداگانه بزنید. در محیط دارای Docker مسیر امن‌تر اجرای `tools/docker_run.sh` است.

## سؤال‌های احتمالی

1. **چرا Base را اجرا می‌کنیم؟** بدون بازتولید خطای اولیه، ادعای درست بودن وصله معتبر نیست و نتیجه INCONCLUSIVE می‌شود.
2. **چگونه ناقص بودن وصله را اثبات می‌کنیم؟** ورودی اولیه و ورودی متفاوت مرزی را روی هر دو نسخه اجرا می‌کنیم؛ اگر یکی همچنان با همان خطای ASan همراه شود، `Incomplete Fix` است.
3. **چگونه رگرسیون را می‌فهمیم؟** ورودی معتبری که با oracle مستقل در Base موفق بوده است، در patched ناموفق می‌شود.
4. **کدام داده به تغییر کد ارتباط داده می‌شود؟** stack frame مربوط به برنامه و hunkهای `git diff`، به همراه نتیجه واقعی قبل/بعد؛ اگر هم‌پوشانی مؤثر پیدا نشود `unknown` گزارش می‌شود.
5. **معنای PASS؟** تنها در دامنه ورودی‌ها و پیکربندی‌های اجراشده، رفع خطای پایه و حفظ رفتار صحیح مشاهده شده، نه اثبات نبود تمامی آسیب‌پذیری‌ها.
6. **چرا Sanitized و Release جدا هستند؟** ابزارگذاری باعث تغییر رفتار اجرایی و دیده‌شدن خطاهای حافظه می‌شود؛ نمی‌توان نتیجه یک باینری را به دیگری نسبت داد.
7. **نقش واقعی json-c؟** پردازش JSON واقعی، اما سرریز مثال در کد ادغام‌شده ایجاد شده است، نه در کد upstream؛ بدون تأیید مدرس نباید آن را یک CVE واقعی معرفی کرد.

## پیش از تحویل

تأیید مدرس درباره دو هدف، مبنای صحت و نتایج مورد انتظار الزامی است. تمام اعضا باید حداقل یک تغییر در بخش مربوط به خود انجام دهند و تست آن را اجرا کنند. تاریخچه Git و شواهد واقعی فعالیت هر فرد باید نگهداری شود.
