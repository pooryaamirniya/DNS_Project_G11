# راهنمای دفاع فردی گروه ۱۱ — PatchGuard

**اعضا:** پوریا امیرنیا، دانیال آذرنیا، محمدجواد خوشدونی فراهانی، محمدمتین انصاری.

**تذکر:** تقسیم زیر صرفاً پیشنهادی برای یادگیری و تمرین دفاع است؛ نباید به‌عنوان ادعای مشارکت واقعی افراد ثبت شود. شرح مشارکت واقعی و شواهد مربوط در `docs/TEAM_CONTRIBUTIONS_TEMPLATE_FA.md` تکمیل شود.

## معماری در یک دقیقه

`JSON Config → Build baseline & candidate (release + sanitized) → Execute tests → ASan/UBSan & output parsing → Crash consensus → Independent functional oracle → Source diff correlation → Minimize & persist regression inputs → Report JSON/MD → CI verdict`

ابزار نام فایل کاندیدا یا وضعیت از پیش اعلام‌شدهٔ آن را برای تشخیص نتیجه به‌کار نمی‌گیرد. یافته‌ها حاصل اجرای واقعی باینری‌ها هستند.

## تقسیم پیشنهادی موضوعات تمرین

| عضو | موضوعی که باید در دفاع مسلط باشد | فایل‌ها / مفهوم |
|---|---|---|
| پوریا امیرنیا | CLI، تصمیم نهایی، کدهای خروج و GitHub Actions | `patchguard/cli.py`، `.github/workflows/` |
| دانیال آذرنیا | اجرای Release/Sanitized، ASan/UBSan و تحلیل پشته | `runner.py`، `detection.py` |
| محمدجواد خوشدونی فراهانی | ارتباط یافته با Diff و ELF Hardening | `correlation.py`، `hardening.py` |
| محمدمتین انصاری | Delta Debugging، Reproducer، تست رگرسیون و Unseen Patch | `minimize.py`، `blind_patch_test.py`، `evaluate_candidate.py` |

## هدف‌های پروژه در دفاع

1. `frame`: هدف آموزشی ساخت گروه با سرریز پشته.
2. `cjsonreal`: سورس **واقعی cJSON** با نسخه‌های upstream `v1.7.17` و `v1.7.18` برای CVE-2024-31755 (ورودی NULL به `cJSON_SetValuestring`). وصله‌های ناقص و دارای رگرسیون، نسخه‌های آزمایشی پروژه هستند و **نباید** با نسخه‌های رسمی upstream اشتباه گرفته شوند.

نمونهٔ قدیمی `targets/jsonc/` در ماتریس اصلی استفاده نمی‌شود.

## اجرای امن برای نمایش زنده

```bash
bash tools/docker_run.sh
python3 tools/blind_patch_test.py
python3 tools/quality_gate.py --strict
```

برای آزمون یک وصلهٔ ناشناخته و سازگار با رابط هدف:

```bash
python3 tools/evaluate_candidate.py --target frame --source candidate_sources/changed.c
```

از اجرای مستقیم برنامهٔ آسیب‌پذیر با `--allow-local` روی سیستم شخصی خودداری کنید؛ اجرای Docker پیش‌فرض امن‌تر است.

## پرسش‌های محتمل

**چرا Base را آزمایش می‌کنیم؟** ابتدا باید وجود خطای پایه به‌صورت قابل‌تکرار تأیید شود. اگر خطا را بازتولید نکردیم، `PASS` قطعی برای اصلاح آن صادر نمی‌کنیم.

**تفاوت SIGSEGV با ASan چیست؟** سیگنال، توقف فرایند را نشان می‌دهد؛ ASan ممکن است نوع دقیق نقض حافظه و پشتهٔ فراخوانی را گزارش کند. هر توقفی لزوماً آسیب‌پذیری تأییدشده نیست.

**تفاوت Incomplete و New Issue؟** برای Incomplete شواهد نشان می‌دهد خطای قبلی با امضای قابل‌مقایسه باقی مانده است؛ New Issue خطای تأییدشدهٔ متفاوتی است. تشخیص با نوع خطا و محل برنامه انجام می‌شود و محدودیت دارد.

**تفاوت رگرسیون عملکردی؟** ورودی معتبری که طبق مرجع مستقل در نسخه پایه رفتار درستی دارد، بعد از وصله رفتار مورد انتظار را ندارد.

**چرا diff correlation اثبات علت نیست؟** هم‌پوشانی تغییرات تابع با Stack Trace فقط شاهد ارتباط است؛ نمی‌تواند به‌تنهایی علیت یا رفع کامل آسیب‌پذیری را ثابت کند.

**چرا Release و Sanitized جدا هستند؟** ابزارگذاری ASan/UBSan رفتار و حافظهٔ فرایند را تغییر می‌دهد. باید هر دو نسخهٔ ساخت و شرایط اجرا جدا ثبت شوند.

**چرا کد ۲۰ در خروجی گروهی طبیعی است؟** چون در ماتریس اصلی عمداً وصله‌های دارای رگرسیون هم داریم. موفقیت مجموعه با `Scenario matrix PASS` و تطابق کدهای **تک‌تک سناریوها** سنجیده می‌شود.

**کدهای ۰، ۱۰، ۲۰، ۳۰، ۴۰ چه هستند؟** ۰=PASS، ۱۰=باقی‌ماندن/خطای جدید امنیتی، ۲۰=رگرسیون عملکردی، ۳۰=خطای ساخت/پیکربندی، ۴۰=ناکافی یا ناپایدار بودن شواهد.

**Hardening چه چیزی را اثبات می‌کند؟** NX، PIE، RELRO و canary وضعیت یا نشانه‌های حفاظت باینری‌اند؛ هیچ‌کدام به‌تنهایی امنیت کامل را تضمین نمی‌کنند.

**چرا ۹/۹ آزمایش Blind کافی نیست؟** این‌ها سناریوهای جدید تولیدشده از هدف‌های موجودند؛ روز دفاع ممکن است وصله یا کد ناشناخته با رفتار پیچیده‌تری مطرح شود.

## تمرین تغییر محدود برای هر نفر

یک شاخهٔ آزمایشی جدا بسازید و از همان شاخه دفاع کنید. نمونه‌های تمرین: افزودن یک Functional Test به config، تغییر آستانهٔ guard در یک variant و مشاهدهٔ نتیجه، افزودن یک Unit Test برای خطاهای Sanitizer، یا بررسی اثر یک گزینهٔ Build روی Hardening. پس از هر تغییر باید اجرای واقعی و گزارش را نشان دهید. تغییرات تمرینی را بدون بازبینی در شاخهٔ `main` ادغام نکنید.

## شرط‌های اداری باقی‌مانده

تأیید مدرس/TA دربارهٔ هدف‌ها و اوراکل‌ها باید مستند شود. همچنین هر فرد باید مشارکت مؤثر و تسلط به بخش مورد دفاع را نشان بدهد؛ موفق بودن CI جایگزین دفاع شخصی نیست.
