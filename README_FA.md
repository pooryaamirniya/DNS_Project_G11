# PatchGuard — پروژهٔ ۱ درس امنیت داده و شبکه، گروه ۱۱

**اعضای گروه:** پوریا امیرنیا، دانیال آذرنیا، محمدجواد خوشدونی فراهانی، محمدمتین انصاری

**مخزن:** https://github.com/pooryaamirniya/DNS_Project_G11

PatchGuard ابزار ارزیابی پویای وصله‌های امنیتی برنامه‌های C/C++ روی Linux x86-64 است. ابزار نسخهٔ آسیب‌پذیر و نسخهٔ وصله‌شده را اجرا می‌کند، یافته‌های ASan/UBSan را استخراج می‌کند، آن‌ها را با تغییرات کد مقایسه می‌کند، آزمون‌های عملکردی را با مرجع مستقل می‌سنجد، ورودی‌های خطاساز را کوچک می‌کند و گزارش JSON/Markdown تولید می‌کند.

## هدف‌های اصلی

- `frame`: برنامهٔ آموزشی نوشته‌شده برای پروژه.
- `cjsonreal`: نسخه‌های واقعی upstream کتابخانهٔ cJSON، نسخهٔ آسیب‌پذیر `v1.7.17` و نسخهٔ وصله‌شدهٔ `v1.7.18` برای CVE-2024-31755. نسخه‌های ناقص و رگرسیونِ این هدف، سناریوهای آزمایشی ساخته‌شده در پروژه هستند؛ نسخهٔ رسمی upstream نیستند.

پوشهٔ قدیمی `targets/jsonc/` صرفاً برای نگهداری نمونهٔ قبلی است و **در ماتریس اصلی ارزیابی استفاده نمی‌شود**.

## اجرا از صفر (WSL2 با Docker Desktop یا Linux)

```bash
git clone https://github.com/pooryaamirniya/DNS_Project_G11.git
cd DNS_Project_G11
bash tools/docker_run.sh
python3 -m unittest discover -s tests -v
python3 tools/blind_patch_test.py
python3 tools/quality_gate.py --strict
```

**ترتیب مهم است:** تست‌های واحد مربوط به ورودی‌های رگرسیونِ یادگرفته‌شده، به فایل‌هایی وابسته‌اند که اجرای نخست PatchGuard تولید می‌کند؛ پس ابتدا Docker matrix را اجرا کنید.

در اجرای ماتریس باید `Scenario matrix PASS` دیده شود. موفقیت ماتریس به معنی کد خروج صفر برای تمام سناریوها نیست؛ نسخه‌های ناقص عمداً `10` و نسخه‌های دارای رگرسیون عمداً `20` می‌دهند. برای آزمایش وصله‌های تولیدشده، هدف `Blind patch matrix: 9/9 passed` است. در مرحلهٔ آخر باید `Quality Gate: PASS` به دست آید.

## آزمون وصلهٔ جدید در دفاع

فایل C را درون پوشهٔ مخزن قرار دهید؛ برای نمونه:

```bash
python3 tools/evaluate_candidate.py --target frame --source candidate_sources/changed.c
```

برای هدف واقعی، `--target cjsonreal` را به‌کار ببرید؛ فایل باید با رابط سناریوی انتخاب‌شده سازگار باشد. نتیجه باید بر اساس اجرای واقعی و گزارش معتبر بررسی شود، نه نام فایل یا فرض اولیه دربارهٔ وصله.

## مستندات و گزارش‌ها

- `docs/architecture.md`: معماری و محدودیت‌ها.
- `docs/oracle-frame.md` و `docs/oracle-cjsonreal.md`: رفتار مرجع و مبنای آزمون‌ها.
- `targets/cjsonreal/source_manifest.json`: منشأ نسخه‌های واقعی cJSON و هش‌های فایل‌ها.
- `artifacts/ci/report.json` و `artifacts/ci/report.md`: گزارش سناریوهای اصلی.
- `artifacts/blind-patches/summary.json`: نتیجهٔ ۹ آزمون تولیدی.
- `artifacts/quality-gate/quality_report.md`: ممیزی شواهد.
- `docs/FINAL_SUBMISSION_CHECKLIST_FA.md`: کنترل نهایی تحویل.
- `docs/TEAM_CONTRIBUTIONS_TEMPLATE_FA.md`: فرم ثبت مشارکت واقعی اعضا.

**محدودیت مهم:** موفقیت CI به معنی اثبات نبود همهٔ آسیب‌پذیری‌ها نیست. همچنین تأیید مدرس برای هدف‌ها و اوراکل‌های مستقل باید جداگانه مستند شود؛ این مخزن ادعای دریافت آن را ندارد. کدهای آسیب‌پذیر را بیرون از محیط ایزوله اجرا نکنید.
